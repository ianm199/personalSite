⏺ Excellent research. Here's the full behavior spec:

  Behavior Spec: Crosslink

  CLI Commands

  - crosslink scan <path> — Scan a directory (or multi-repo root) and store
  discovered services, endpoints, and calls in SQLite (flags: --db, --exclude,
  --proto-dir)
  - crosslink tree — Display the dependency tree from stored scan data (flags:
  --root, --depth, --format [text|json|dot])
  - crosslink cycles — Detect and display circular dependencies (flags: --format
   [text|json])

  Data Model (SQLite)

  - services → name, language, framework, root_path
  - endpoints → service_id, method, route, source_file, line_number,
  proto_service, proto_method
  - calls → service_id, target_url_or_method, source_file, line_number,
  call_type (http|grpc)
  - edges → source_service_id, target_service_id, call_id, endpoint_id (resolved
   links)

  Extraction Strategy (the hard part)

  Two-sided matching:
  1. Server extractors — find endpoints each service exposes (decorators, route
  registrations, gRPC service implementations)
  2. Client extractors — find outbound calls each service makes (requests.get,
  grpc stubs, custom client wrappers)
  3. Resolver — matches calls → endpoints by URL pattern, gRPC service/method,
  or proto definition

  Must handle messy patterns:
  - Direct URLs: requests.get("http://checkout:8080/api/place-order")
  - Client wrappers: self.stub.GetProduct(request) (gRPC)
  - Framework patterns: @app.route("/cart"), router.HandleFunc("/products", 
  handler)
  - String concatenation and f-strings where feasible

  Extractors (per-language, all independent — parallelize)
  Language: Python
  Server Frameworks: FastAPI, Flask, Django, gRPC servicer
  Client Patterns: requests, httpx, grpc stubs
  Parsing: tree-sitter-python
  ────────────────────────────────────────
  Language: Go
  Server Frameworks: net/http, gorilla/mux, gin, gRPC server
  Client Patterns: net/http client, grpc.Dial
  Parsing: tree-sitter-go
  ────────────────────────────────────────
  Language: Java
  Server Frameworks: Spring Boot (@RequestMapping etc), gRPC
  Client Patterns: RestTemplate, WebClient, gRPC stubs
  Parsing: tree-sitter-java
  ────────────────────────────────────────
  Language: C#
  Server Frameworks: ASP.NET Core ([HttpGet] etc), gRPC
  Client Patterns: HttpClient, gRPC channel
  Parsing: tree-sitter-c-sharp
  ────────────────────────────────────────
  Language: JS/TS
  Server Frameworks: Express, Fastify, NestJS, gRPC
  Client Patterns: fetch, axios, node-fetch, grpc stubs
  Parsing: tree-sitter-typescript
  Plus: Proto file parser — extracts service/method definitions from .proto
  files to link gRPC calls to implementations.

  Training Data (3 repos)

  1. Google Online Boutique (GoogleCloudPlatform/microservices-demo) — 11
  services, 5 languages, all gRPC. Primary training target.
  2. Train Ticket (FudanSELab/train-ticket) — 41 services, Java/JS/Python/Go,
  HTTP REST. Stress-tests scale.
  3. Sock Shop (microservices-demo/microservices-demo) — 8 services,
  Go/Java/Node.js, REST APIs.

  Test Data (2 held-out repos)

  1. Istio Bookinfo (istio/istio samples/bookinfo) — 4 services, 4 languages,
  simple HTTP chain.
  2. Microsoft eShop (dotnet/eShop) — C# focused, HTTP + gRPC + event-driven.

  Build Plan

  - Phase 1 (sequential): Scaffold — pyproject.toml, package structure, core
  models/enums, venv, verify imports
  - Phase 2 (4 parallel agents): Foundation — SQLite storage layer, extractor
  protocol + registry, tree-sitter setup + language registry, proto file parser
  - Phase 3 (6 parallel agents): Implementation — Python extractor, Go
  extractor, Java extractor, C# extractor, JS/TS extractor, scanner/resolver
  pipeline
  - Phase 4 (2 parallel agents): Interface — CLI commands (Typer), output
  formatters (Rich tables, tree view, DOT graph)
  - Phase 5: Training validation — scan all 3 training repos, compare against
  ground truth, iterate
  - Phase 6: Test generalization — scan held-out repos, report accuracy

  Does this look right? Say 'go' to start building, or tell me what to change.
